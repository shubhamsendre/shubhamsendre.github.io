What This Was Supposed to Be (and Why It Changed)

This started as a straight Pixi-vs-uv comparison: install the same production bioinformatics environment with both, time it, compare lockfiles. That post doesn’t exist, because the premise doesn’t survive contact with reality.

uv cannot install bioconda packages. It is a PyPI-and-Python-interpreter tool, full stop. Its maintainers have an open issue requesting conda-channel support, opened in February 2024, explicitly tagged “not on the immediate roadmap.” STAR, Salmon, samtools, FastQC — the actual tools a pipeline like nf-core/rnaseq depends on — are compiled binaries distributed through bioconda, not Python wheels on PyPI. uv cannot see them, let alone install them.

So this is a Pixi vs. conda/mamba post instead, which is where the real comparison lives. uv gets one section near the end, because Pixi actually uses it internally for the pure-Python slice of a project — that’s the honest role it plays here.

The Task: Reproduce a Real Pipeline’s Dependencies

nf-core/rnaseq is a widely-used, production Nextflow pipeline. I pulled its dependency declarations at tag 3.27.0 — 74 module-level environment.yml files, covering everything from fastqc to bioconductor-deseq2.

The obvious first move — combine all 74 files into one environment and install it once — fails, and how it fails is itself informative.

Finding 1: You Can’t Combine Them Into One Environment

Different modules pin different versions of the same package, because each module only ever runs in its own container or environment in production — nobody has ever needed all 74 to agree on one shared set. Combining them surfaces that immediately:

Package Conflicting pins across modules
python 3.9.18, 3.12.2, 3.12.12, 3.14.5
samtools / htslib 1.21 and 1.24
r-base 4.3 and 4.4.2
gawk 5.1.0 and 5.3.1
sed 4.7 and 4.8

Taking the highest pin for each and resolving the combined set still fails — not just on these six, but broadly. Conda’s solver rejects it on perl=5.26.2 (a 2017 release incompatible with newer package builds), multiqc, preseq, sentieon, and umi_tools, on top of the version splits above. Splitting into three coarser groups (core bioconda tools, the R/Bioconductor stack, sortmerna alone — isolated because its package has Python-build variants that clash with the rest) still doesn’t fully resolve it.

The only granularity that actually works is nf-core’s own: one environment per module. That’s not a limitation of this benchmark — it’s confirmation that nf-core’s container-first design (Docker/Singularity per process, with -profile conda kept as an explicit last resort in its own docs) is the only architecture that was ever going to hold together.

Finding 2: Per-Module, All Three Tools Just Work

With that constraint accepted, I benchmarked conda, mamba, and Pixi installing each of the 74 module environments independently — cold cache (cleared before each tool’s run) and warm cache (repeated right after), one pass each.

Results

Tool Cold total (74 modules) Cold avg/module Warm total Warm avg/module
conda 820.2 s 11.08 s 488.8 s 6.61 s
mamba 683.6 s 9.24 s 381.4 s 5.15 s
Pixi 590.1 s 7.97 s 263.0 s 3.55 s

Pixi wins on both cold and warm installs, and the gap widens on warm cache — 3.55s/module average against conda’s 6.61s, nearly 2x. mamba sits in between, as expected for a faster conda-compatible solver that still shares conda’s package-handling machinery.

An Honest Caveat on These Numbers

This is n=1 per cell — one cold run, one warm run, per tool, per module. These are point estimates, not statistically robust averages. I’d want 3-5 repetitions per cell before trusting the Pixi-vs-mamba gap specifically (9% faster cold, 31% faster warm) to hold up; the conda-vs-Pixi gap is large enough (27% cold, 46% warm) that it’s unlikely to be noise, but treat the exact numbers as directional, not definitive.

One run also hit a real anomaly worth disclosing rather than hiding: Pixi’s cold run on rseqc/junctionannotation initially logged 47,950 seconds — clearly not a real solve time. A clean re-run of the identical spec took 66.5 seconds, in line with six other modules sharing the same two-package set. The likely cause: this machine’s disk hit 99% full partway through the run (my own accumulated package caches were part of that), and I/O under near-zero free space can stall arbitrarily. I’ve reported the clean reproduction value in the table above, not the stall, and disclosed it here instead of pretending it didn’t happen. Five other cells (one mamba failure, four pixi warm-pass failures) failed with explicit ENOSPC errors during that same disk-pressure window and were re-run cleanly afterward with headroom restored.

Finding 3: Reproducibility — Both Work, for Different Reasons

I installed the most complex module (deseq2_qc, 9 packages spanning R and Bioconductor) twice, independently, with both tools, and diffed the result:

  • Pixi: pixi.lock was byte-identical across both installs.
  • conda: conda list --explicit output (which pins exact build strings, not just versions) was also identical across both installs.

Both reproduce exactly here — which isn’t actually the interesting finding, given every package in this test was already pinned to an exact version. The real difference is structural, not about single-run determinism:

  • Pixi generates pixi.lock automatically, every time, covering the whole resolved graph with hashes, committed alongside the project by default.
  • conda’s reproducibility is opt-in and manual. conda create and conda env create -f environment.yml don’t produce a lock file. You have to remember to run conda list --explicit yourself, after the fact, and keep that output somewhere. nf-core’s own module environment.yml files — the actual input to the -profile conda path — carry no lock file at all; they pin top-level versions but say nothing about transitive dependencies or build strings, which can drift as the channel index changes over time.

So the honest claim isn’t “Pixi is more reproducible than conda in a single run” — it’s “Pixi makes reproducibility the default behavior; conda makes it something you have to deliberately opt into and maintain yourself.”

Where uv Actually Fits

uv isn’t absent from this story — it’s just not competing in it. Pixi uses uv internally to resolve and install any PyPI-only dependencies a project declares alongside its conda packages (via Pixi’s [pypi-dependencies] table). So the realistic role for uv in a bioinformatics pipeline isn’t “replace conda” — it’s “handle the pure-Python tooling around the pipeline” — custom analysis scripts, nf-core-tools itself, anything with no bioconda-only binary dependency — while Pixi (or conda/mamba) handles the actual tool binaries. Poetry sits in the same category as uv here: PyPI-only, no bioconda reach, useful for the Python-only slice and nothing else.

Reproducing This

# Pull the pinned pipeline version and extract per-module specs
git clone --depth 1 --branch 3.27.0 https://github.com/nf-core/rnaseq.git

# For a single module, install with each tool (example: fastqc)
conda create -y -p /tmp/env-conda -c conda-forge -c bioconda --override-channels fastqc=0.12.1
mamba create -y -p /tmp/env-mamba -c conda-forge -c bioconda --override-channels fastqc=0.12.1
pixi init /tmp/env-pixi && cd /tmp/env-pixi && pixi add -c conda-forge -c bioconda fastqc==0.12.1

# Reproducibility check
conda list -p /tmp/env-conda --explicit   # re-run install, diff this output
cat pixi.lock                              # re-run pixi install, diff this file

The full per-module benchmark script, the 74-module spec extraction, and the raw results (module_benchmark.csv) are in this post’s source directory.
