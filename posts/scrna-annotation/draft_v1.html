What This Is (and Isn’t)

Once you’ve clustered a single-cell RNA-seq dataset, you’re left with the same question every time: what is cluster 4, actually? This post walks through three ways to answer that — a reference-based classifier (CellTypist), classical marker-gene scoring, and an LLM reading each cluster’s top differentially expressed genes — run on the same dataset, so their agreements and disagreements are directly comparable.

It is not a benchmark paper. One dataset, nine clusters, no ground-truth FACS labels to score against — just three legitimate methods, run side by side, with an honest look at where they line up and where the disagreement is actually informative rather than a bug.

The Dataset: PBMC3k

PBMC3k is 10x Genomics’ public demo dataset — 2,700 peripheral blood mononuclear cells, sequenced with an early 10x Chromium chemistry, and the same dataset the canonical Scanpy PBMC3k tutorial uses. It’s small, public, and has been independently annotated by enough people that its expected cell types (T cell subsets, B cells, monocytes, NK cells, dendritic cells, platelets) are well established — which makes it a reasonable dataset to sanity-check three annotation methods against, even without a formal ground truth.

Standard preprocessing: filter cells with fewer than 200 genes and genes in fewer than 3 cells, drop cells with more than 20% mitochondrial reads, normalize to 10,000 counts and log1p-transform, select the top 2,000 highly variable genes, PCA to 50 components, and Leiden clustering at resolution 1.0. This produced 2,698 cells across 9 clusters.

Method 1: Reference-Based Annotation with CellTypist

CellTypist is a logistic-regression classifier trained on large, curated reference atlases — here, the Immune_All_Low model, trained for fine-grained immune cell subtypes. It predicts a label per cell, plus a probability for every candidate label, and optionally runs majority voting: given an independent over-clustering (Leiden, in this case), it assigns the cluster’s dominant per-cell label to every cell in that cluster, smoothing out noisy individual calls.

Both outputs matter for different reasons: the per-cell labels reveal within-cluster heterogeneity a single cluster-level name would hide; the majority-voted labels give a clean, one-label-per-cluster summary that’s easier to report and compare against the other two methods.

Method 2: Marker-Gene Scoring — the Classical Baseline

No training, no reference atlas — just canonical PBMC marker gene sets (CD3D/CD3E for T cells, MS4A1/CD79A for B cells, GNLY/NKG7 for NK cells, CD14/LYZ for classical monocytes, FCGR3A/MS4A7 for non-classical monocytes, FCER1A/CST3 for dendritic cells, PPBP/PF4 for platelets, and CD8-specific markers for cytotoxic T cells). Each cluster’s mean sc.tl.score_genes score is computed against every marker set, and the cluster is assigned whichever set scores highest.

This is the annotation equivalent of a hand-tuned rule — transparent and fast, but only as good as the marker panel you wrote down in advance. It can’t discover a cell type you didn’t already have a gene list for.

Method 3: An LLM Reading Marker Genes

For each cluster, sc.tl.rank_genes_groups (Wilcoxon test) produces its top 10 differentially expressed genes. Those gene symbols — nothing else, no cluster statistics, no prior labels — are handed to an LLM with a fixed prompt asking for the single most likely PBMC cell type:

“Given the top differentially expressed marker genes for one cluster, return the single most likely immune cell type… Top marker genes (highest to lowest significance): {genes}”

Two choices matter for reproducibility here: the model is pinned to a specific version and called with temperature=0, so the same marker list produces the same label on every rerun rather than drifting between calls; and every prompt/response pair is logged and cached to disk, so re-running the offline script during iteration doesn’t re-call (or re-bill) the API for clusters that haven’t changed.

The appeal is obvious: zero marker-panel curation — the model brings its own prior knowledge of immunology instead of a hand-written gene list. The risk is just as real: an LLM can produce a fluent, confident, wrong label with no calibrated uncertainty attached, and it has no way to say “I don’t recognize this” the way a low CellTypist probability can.

Try It: Interactive Comparison

The panel below is a full marimo notebook running in your browser via WebAssembly (Pyodide) — no server, no Python install on your end.

One honest caveat on how this is built: none of scanpy, anndata, or CellTypist’s scikit-learn backend are verified to run inside a browser’s WASM sandbox, so all three methods above were run once, offline, and their outputs — UMAP coordinates, per-cell and per-cluster labels, confidence scores, the agreement statistics — were saved as small CSV/JSON files. What is genuinely live in the notebook: recoloring the UMAP by any of the four label sets, filtering cells by CellTypist confidence, and browsing the per-cluster table — all pure pandas/NumPy/Matplotlib, recomputed in your browser every time you touch a control.

At the broad cell-type level, the two methods agree on all nine clusters. Every disagreement is a resolution mismatch, not a contradiction: the marker-gene baseline’s fixed panel names a broad category (“T cells,” “NK cells”), while CellTypist’s finer reference model names a specific subtype within it (“Tcm/Naive helper T cells,” “CD16+ NK cells”). That’s the expected failure mode of a hand-picked marker panel — not wrong, just lower resolution than a model trained on a much larger labeled reference.

How much does CellTypist’s per-cell typing agree with the clusters themselves?

CellTypist assigns every cell a label independently — it never sees the Leiden partition. Comparing its raw per-cell labels against the Leiden clusters with the Adjusted Rand Index gives 0.449. That’s meaningfully below 1.0, and it should be: the confusion matrix in the notebook shows CellTypist splitting single Leiden clusters (especially cluster 0, the largest T-cell cluster) across several related subtypes — Tcm/Naive helper T cells, Tem/Effector helper T cells, Treg, MAIT cells — rather than just re-deriving the same 9 groups under a different name. A majority-voted, one-label-per-cluster summary (like the table above) is convenient, but it genuinely erases that heterogeneity.

Discussion: When to Trust Which

  • Broad-category calls are cheap to get right; subtype calls are where methods diverge. If you only need “lymphocyte vs. myeloid,” any of these three methods will likely agree. Subtype-level annotation is where the choice of method — and its reference panel’s resolution — actually matters.
  • CellTypist’s confidence scores are directly actionable. Because it outputs a real probability per cell, you can filter to “only the calls I’m confident in” and manually review the rest — see the confidence slider in the notebook above. Neither the marker-gene baseline nor a plain LLM label comes with a comparably calibrated uncertainty signal.
  • LLM annotation trades curation cost for hallucination risk. No marker panel to write and maintain, but also no guarantee the label is grounded in anything beyond the model’s prior — and unlike CellTypist, it can’t natively flag “this doesn’t look like any cell type I know.” Treat it as a fast first pass to be checked, not a final call.
  • None of this generalizes across tissue or disease state without re-checking. PBMC3k is about as friendly a dataset as scRNA-seq annotation gets — a well-studied tissue with a mature reference model. Solid tumor or disease-state datasets, where CellTypist’s training distribution is a worse match and marker panels are less standardized, will show more disagreement between all three methods than this post does.

Reproducing This

  • Offline stage (generate_artifacts.py): downloads PBMC3k, runs the standard Scanpy preprocessing/clustering pipeline, runs CellTypist (Immune_All_Low model with majority voting), scores the marker-gene baseline, calls an LLM per cluster for the third annotation, computes the agreement statistics, and writes the small artifacts this notebook loads. The LLM step reads its API key from the ANTHROPIC_API_KEY environment variable only — never hardcode it — and caches every response to disk so reruns don’t re-call the API for unchanged clusters.
  • Interactive stage (notebook.py): the marimo notebook above. Needs only numpy, pandas, matplotlib, and marimo — all WASM-compatible, which is why it can ship as a static page with no server behind it.
# offline (heavy env: scanpy, anndata, celltypist, anthropic)
export ANTHROPIC_API_KEY=...
conda run -n scanpy python generate_artifacts.py

# interactive notebook, locally
conda run -n quarto-blog marimo edit notebook.py

# export the interactive layer to a static, browser-runnable bundle
conda run -n quarto-blog marimo export html-wasm notebook.py -o notebook_wasm --mode run
