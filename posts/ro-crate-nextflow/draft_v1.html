The Problem RO-Crate Was Built to Solve

A folder of pipeline outputs is opaque. Raw files sitting on a server answer none of the questions anyone actually needs answered:

  • What tool produced this VCF? At what version?
  • What input data was used? Are the checksums the same?
  • Who ran this? When? On what infrastructure?
  • Can I re-run it and get the same result?

The bioinformatics community has tried to solve this before. Research Objects — the conceptual predecessor to RO-Crate — proposed bundling research materials with rich linked data metadata. The idea was sound. The adoption was not. The technology stack required (OWL ontologies, SPARQL, full RDF toolchains) was too steep for most working scientists and engineers.

RO-Crate is the pragmatic successor. It was designed, as Soiland-Reyes et al. put it, to use “just enough Linked Data” — structured metadata that is machine-readable and semantically interoperable, but accessible to anyone who can write JSON1.

What RO-Crate Actually Is

An RO-Crate is a directory — any directory — with a single file added: ro-crate-metadata.json. That file uses JSON-LD and schema.org vocabulary to describe what is in the directory, who created it, what software was involved, and how the contents relate to each other.

JSON-LD is the key design choice here. It looks like ordinary JSON, which means any developer can read and write it without learning a new toolchain. But it carries semantic meaning: every field maps to a well-defined concept in an internationally agreed vocabulary. A Person entity in your metadata means the same thing as a Person in a Harvard data repository or a European health data space.

The spec defines three types of entities:

Entity Type What It Describes Example
Root Data Entity The crate itself — the top-level research output The pipeline run directory
Data Entities Files and directories inside the crate results/annotated.vcf.gz, samplesheet.csv
Contextual Entities Things referenced from outside A Person, a SoftwareApplication, an Organisation

The FAIR Guiding Principles2 — Findable, Accessible, Interoperable, Reusable — are the stated goal. RO-Crate is the practical mechanism for achieving them without requiring semantic web expertise.

Two Levels of RO-Crate in a Nextflow Context

Before writing any JSON, it helps to understand that RO-Crate applies at two distinct levels in a Nextflow pipeline:

Level What It Describes When It Exists
Pipeline-level The workflow itself — purpose, authors, license, inputs, outputs Once per pipeline, committed to the repo
Run-level A specific execution — input files, parameters, container versions, timestamps Generated fresh per pipeline run

Both are valid RO-Crates. They serve different purposes. The pipeline-level one makes your workflow a citable, discoverable artifact on WorkflowHub. The run-level one is your audit trail and reproducibility record.

Pipeline-Level RO-Crate: Describing Your Workflow

The pipeline-level ro-crate-metadata.json lives in the root of your repository. It describes your workflow as a ComputationalWorkflow — a scientific artifact with a name, authors, license, and formal descriptions of its inputs and outputs.

The Minimal Structure

Every valid RO-Crate metadata file has two required entries in its @graph:

{
  "@context": "https://w3id.org/ro/crate/1.1/context",
  "@graph": [
    {
      "@id": "ro-crate-metadata.json",
      "@type": "CreativeWork",
      "conformsTo": {"@id": "https://w3id.org/ro/crate/1.1"},
      "about": {"@id": "./"}
    },
    {
      "@id": "./",
      "@type": ["Dataset", "ComputationalWorkflow"],
      "name": "my-annotation-pipeline",
      "description": "A Nextflow pipeline for variant annotation using VEP, FastQC, and MultiQC.",
      "license": "MIT",
      "version": "1.0.0",
      "programmingLanguage": {
        "@id": "https://w3id.org/workflowhub/workflow-ro-crate#nextflow"
      },
      "author": [{"@id": "#author-1"}],
      "input": [{"@id": "#input-samplesheet"}],
      "output": [{"@id": "#output-vcf"}]
    }
  ]
}

The first entry (ro-crate-metadata.json) is always the metadata descriptor — it points to ./ as its subject. The second entry (./) is the root dataset — your pipeline.

Adding Authors

{
  "@id": "#author-1",
  "@type": "Person",
  "name": "Shubham Sendre",
  "affiliation": "Invisibl Cloud Solutions Pvt. Ltd.",
  "url": "https://orcid.org/0000-0000-0000-0000"
}

Use your ORCID as the @id if you have one — it makes the pipeline citable in academic contexts and is how WorkflowHub links pipeline authorship to your research identity.

Describing Inputs and Outputs

FormalParameter entries are what make the pipeline machine-readable. WorkflowHub parses these to display pipeline interfaces:

{
  "@id": "#input-samplesheet",
  "@type": "FormalParameter",
  "name": "input",
  "description": "Samplesheet CSV with sample IDs and paths to FASTQ files",
  "encodingFormat": "text/csv"
},
{
  "@id": "#output-vcf",
  "@type": "FormalParameter",
  "name": "annotated_vcf",
  "description": "VEP-annotated VCF with functional consequence predictions",
  "encodingFormat": "text/tab-separated-values"
}

Referencing Software Dependencies

Use bio.tools identifiers where they exist — they are the standard registry for bioinformatics tools and the identifiers WorkflowHub recognises:

{
  "@id": "https://bio.tools/vep",
  "@type": "SoftwareApplication",
  "name": "Ensembl VEP",
  "version": "110.1",
  "url": "https://www.ensembl.org/vep"
}

Add this to hasPart or softwareRequirements on the root Dataset node.

Run-Level RO-Crate: Provenance with nf-prov

The pipeline-level RO-Crate describes your workflow as a static artifact. Run-level provenance captures what actually happened in a specific execution.

This is where the W3C PROV data model3 becomes relevant. PROV defines a standard vocabulary for describing entities (data), activities (processes), and agents (people/software) and the relationships between them. The nf-prov plugin translates Nextflow execution events into a PROV-conformant RO-Crate automatically.

Enabling nf-prov

Add to your nextflow.config:

plugins {
  id 'nf-prov@1.2.2'
}

prov {
  enabled = true
  formats {
    rocrate {
      file = "${params.outdir}/pipeline_info/ro-crate-metadata.json"
    }
  }
}

What Gets Captured Per Run

After every pipeline execution, nf-prov writes an ro-crate-metadata.json into your output directory that records:

  • Workflow version (exact git commit or tag)
  • Input files with checksums (MD5/SHA256)
  • Output files with checksums and sizes
  • Start and end timestamps per process
  • Container image IDs used per process
  • Full resolved parameter set at runtime

A fragment of what the run record looks like:

{
  "@id": "#run-2026-04-15",
  "@type": "CreateAction",
  "instrument": {"@id": "main.nf"},
  "startTime": "2026-04-15T09:23:11Z",
  "endTime": "2026-04-15T11:47:32Z",
  "object": [{"@id": "inputs/samplesheet.csv"}],
  "result": [{"@id": "results/annotated.vcf.gz"}]
}

This is the difference between “I ran the pipeline” and “I can prove exactly what ran, on what input, at what time, and what came out.”

Publishing to WorkflowHub

WorkflowHub is the community registry for FAIR scientific workflows. It reads your pipeline-level ro-crate-metadata.json directly to:

  • Display pipeline metadata, authors, description, and inputs/outputs
  • Assign a DOI to your pipeline version, making it citable in publications
  • Link to bio.tools and Bioschemas entries for referenced software
  • Index your pipeline for discoverability across the research community

Registering is straightforward: provide a link to your repository or upload a zip, and WorkflowHub validates your RO-Crate and creates a landing page with a persistent identifier.

A DOI-backed WorkflowHub entry is a concrete portfolio artifact — a versioned, citable record with your name on it that you can link from a CV or LinkedIn profile.

Why This Matters Beyond Good Practice

Reproducibility is shifting from optional to expected. Journals and funders increasingly require that computational analyses be reproducible. An nf-prov RO-Crate is concrete evidence — not “here’s the code”, but “here’s the exact execution with checksums on every input and output.”

External delivery has a provenance question. Delivering pipeline outputs to pharma companies, hospitals, or research institutes often comes with the question: can you prove what ran? An RO-Crate run record is a ready-made answer that doesn’t require trust — it’s self-describing and verifiable.

Regulated environments are where this becomes load-bearing. Trusted Research Environments (TREs) — secure compute environments for sensitive clinical data used in NHS, UK Biobank, and EU health data spaces — require data provenance and audit trails by design. RO-Crate is one of the standards being evaluated and adopted to satisfy those requirements. That last point is where this gets genuinely interesting, and it’s where Part 2 of this series picks up.

Quick Reference: From Zero to FAIR Pipeline

Step Action Time
1 Create ro-crate-metadata.json in pipeline root 30 min
2 Add authors (with ORCID), description, keywords, I/O parameters 20 min
3 Add bio.tools IDs for your software dependencies 15 min
4 Enable nf-prov in nextflow.config 10 min
5 Run pipeline, inspect generated run-level RO-Crate 20 min
6 Register pipeline on WorkflowHub for a DOI 30 min
